# 대화 기억 저장

## 저장 위치

`D:\claude\memory\`

이 경로는 `~/.claude/settings.json`의 `autoMemoryDirectory`로 지정된 전역 메모리
디렉터리다. 사용자 전역 설정이라 모든 프로젝트가 이 폴더를 공유한다. 시스템 프롬프트에
그 세션의 메모리 경로가 따로 안내돼 있으면 그쪽을 우선한다.

## 원칙: 한 파일 = 한 사실

세션 전체를 파일 하나에 몰아넣지 않는다. 나중에 관련성으로 골라 읽히는 구조이므로,
독립적으로 쓸모 있는 사실은 각각 자기 파일을 갖는다. 파일 이름은 세션 날짜가 아니라
**내용**을 가리키는 슬러그로 짓는다.

- 좋음: `bang-prompt-shell-is-git-bash.md`, `branch-cleanup-policy.md`
- 나쁨: `session-2026-08-24-여러가지.md` (여러 사실이 한 파일에 섞임)

날짜가 본질인 기록(그날 삭제한 브랜치의 복구용 SHA 등)만 예외로 날짜를 담되,
그 경우에도 파일 하나에 그 사실 하나만 담는다.

## 순서

1. 대화에서 **다음 세션에도 쓸모 있는 사실**만 골라낸다. 개수는 보통 1~6개다.
   아래 "저장하지 않을 것"에 걸리는 항목은 여기서 버린다.
2. 메모리 디렉터리의 기존 파일을 먼저 훑는다(`MEMORY.md` + 파일 목록).
   이미 그 사실을 다루는 파일이 있으면 새로 만들지 말고 그 파일을 갱신한다.
   틀린 것으로 밝혀진 메모리는 삭제한다.
3. 사실마다 파일 하나씩 Write한다. 형식은 아래 참조.
4. `MEMORY.md`에 파일마다 한 줄씩 포인터를 추가한다:
   `- [제목](파일명.md) — 짧은 훅`
   `MEMORY.md`는 매 세션 컨텍스트에 로드되는 목차다. 본문 내용을 여기 넣지 않는다.
5. 저장·갱신·삭제한 파일을 각각 나열하고, 메모리 파일 개수가 몇 개에서 몇 개로
   바뀌었는지 사용자에게 알려준다.

## 파일 형식

```markdown
---
name: <파일명과 같은 kebab-case 슬러그>
description: <한 줄 요약 — 나중에 관련성 판단에 쓰인다>
metadata:
  type: user | feedback | project | reference
---

<사실 본문. feedback·project 는 아래 두 줄을 이어 붙인다.>

**Why:** <왜 그런지 / 어떤 문제 때문에 정해졌는지>
**How to apply:** <다음에 어떻게 행동하면 되는지>

관련: [[다른-메모리-이름]]
```

### type 고르기

- `user` — 사용자가 누구인지 (역할, 전문성, 선호)
- `feedback` — 일하는 방식에 대한 사용자의 지시. 교정뿐 아니라 승인된 방식도 포함
- `project` — 코드나 git 히스토리에서 유추할 수 없는 진행 중인 작업·목표·제약
- `reference` — 외부 자원 포인터 (URL, 대시보드, 티켓, 저장소 경로)

관련된 다른 메모리는 본문에서 `[[메모리-이름]]`으로 링크한다. 아직 없는 이름을
링크해도 된다 — 나중에 쓸 만한 메모리를 표시해 두는 뜻이다.

## 저장하지 않을 것

- 저장소가 이미 기록하는 것: 코드 구조, 과거 수정 내역, git 히스토리, CLAUDE.md
- 이번 대화 안에서만 의미 있는 것: 중간 과정, 시도했다 버린 방법, 도구 출력
- 시간이 지나면 틀려질 값: 도구 버전 번호, 임시 경로, 진행률
- 사용자가 이런 항목을 기억하라고 하면, 그 안에서 **유추하기 어려웠던 부분**이
  무엇이었는지 되묻고 그것을 대신 저장한다.

## 규칙

- 사실만 적는다. 추측이나 각색은 넣지 않는다.
- 날짜는 "어제", "지난주" 같은 상대 표현 대신 절대 날짜로 적는다.
- 비밀번호, API 키, 토큰 값은 절대 본문에 적지 않는다. "키는 설정 파일에 있음"처럼
  위치만 적는다.
- 저장에 실패하면 완료했다고 말하지 말고 오류 내용을 그대로 보여준다.
